# 启动、关停、重启与推理等待

更新：2026-10-31。

项目根目录 `E:\QQbot` 提供三个入口：

| 脚本 | 操作 |
|---|---|
| `start-all.bat` | 启用 DSH-Web、Harmonia-Autostart 任务，启动全局 DSH、SnowLuma 和 QQ/微信桥接；已经运行时不重复启动 |
| `stop-all.bat` | 先禁用并停止两个自动拉起任务，再结束桥接、SnowLuma 和全局 DSH 的服务进程树；保持关闭直到再次启动 |
| `restart-all.bat` | 顺序执行完整关停和启动，加载新的代码与配置，并恢复静默自启/自动恢复 |

三个 BAT 均调用 `Harmonia/scripts/manage-services.ps1`。原 `Harmonia/start-all.bat` 已移除。双击手动操作时会显示状态窗口，后台服务仍隐藏运行；失败时保留窗口供查看错误。

QQ 客户端、微信客户端、代理程序不随服务关停退出；不清除登录、人设或任何记忆。启动时 SnowLuma 会重新连接已经登录的小号。QQ 凭证失效时仍需本人重新登录。

**DSH 是全局共享服务**，整套关停/重启会中断其他正在使用这个 DSH Web 实例的项目，以及正在执行的 agent/工具任务。进程筛选限定本项目服务路径和全局 DSH Web 启动入口，不批量结束所有 Node、QQ 或 PowerShell。

状态检查：

```powershell
Invoke-RestMethod http://127.0.0.1:8080/health
Get-ScheduledTask -TaskName DSH-Web,Harmonia-Autostart
```

正常预期是 `brainReady=true`、`qqConnected=true`、`wechat=polling`。刚启动的 QQ 自动接入需要数秒；脚本启动成功不等于凭证和模型调用永远有效。

## 推理超时修复

旧配置的 `BRAIN_TIMEOUT_MS=120000` 是整轮固定上限：无论模型是否仍在输出、工具是否有进展，到两分钟就取消 DSH。这会中断原本可能成功的长请求。

现在 DSH 使用两级等待：

```dotenv
BRAIN_TIMEOUT_MS=180000
BRAIN_MAX_TURN_MS=900000
```

- 3 分钟没有新的 DSH 会话事件或流式输出时，以 `DSH_IDLE_TIMEOUT` 结束。每次真实会话事件/输出会续期无进展计时，单纯 WebSocket 连着或 ping 不续期。
- 整轮最多 15 分钟，以 `DSH_TURN_TIMEOUT` 结束，防止永远输出或卡住占据队列。模型思考、工具执行及提供商内部重试都包含在整轮时间内。
- DSH 的 assistantStream 已接入，模型生成中的输出也作为进展；最终只向客户端发送完整最后回复，不发送中间推理或工具前的过程文字。
- 终态的 server_busy 单独记为 `DSH_BUSY`，其他提供商失败为 `DSH_UPSTREAM_ERROR`；不会再被统一覆盖成“没有回复”。
- 私聊发生推理超时或失败时，会收到一条不含技术凭证的失败通知。通知也受持久去重保护。群聊不额外发送失败提示，避免刷屏。

桥接不会自动重跑完整 agent 轮次；某些工具或文件操作可能已发生，重跑可能重复执行。不确定的发送也不自动重发。旧的两条失败私聊没有补发；用户重新发送消息会进入新轮次。

等待上限不能保证提供商恢复，也不能让无流式输出的服务器无限等待。可按实际需求调整两个参数并运行根目录 restart-all.bat。共享处理队列仍串行，某一轮长时间等待会延后后续消息。

验证：新增本机 WebSocket 测试覆盖进展续期、无进展超时、硬上限、server_busy、私聊只通知一次且不重复推理；另有进程选择测试确认 QQ、其他 Node 应用和 DSH headless 不被误选。全部 32 项测试通过。实际整套关停/启动/重启状态见 VALIDATION.md；没有故意向真实提供商制造长时间拥塞。
